# Тесты

Тесты написаны на JUnit 5 + Mockito, лежат в `src/test/java`. Всего их **150, все проходят** (сборка - `./mvnw clean test`).

Покрытие строк ~72%. Порог покрытия (JaCoCo, 0.70) задан в `pom.xml` и проверяется автоматически на фазе `test` - если покрытие упадёт ниже порога, сборка завершится ошибкой.

## Отчёт о покрытии

HTML-отчёт JaCoCo лежит в [coverage/](src/test/coverage/index.html) - откройте `index.html` в браузере, чтобы увидеть покрытие по каждому классу и методу.

## Что не тестируется

Автотесты сознательно не покрывают:

- **Реальную работу с сетью** (`ApiHandler`, а также отправку HTTP-запросов) - это интеграционный уровень; без подмены `HttpClient`/тест-сервера юнит-тесты тут бессмысленны, а запросы на реальные сервисы с плейсхолдер-ключами из `apis.json` не выполняются.
- **Конкурентную часть** (`PollingManager` - планировщик, семафор, запись) - её поведение требует интеграционного/нагрузочного теста с заглушенными HTTP-моками; простой юнит-тест был бы нестабилен по таймингам.
- **Блокирующие интерактивные потоки и работу с файловой системой** (`UserInteraction.interact()/startPolling/runInteractive/runAutomatic`) - покрываются только чисто вспомогательные методы; остальные ветки - через мок.
- **Пограничные сценарии реального запуска** - вывод при не-200 ответах, отсутствующий файл на диске и т.п.

Отдельное замечание: поле `outputApiIDs` (`UserResponse`, выбор "какие API выводить") собирается, но нигде не используется - в файл пишутся все опрошенные API. Похоже на запланированную, но недоделанную фичу фильтрации вывода.
